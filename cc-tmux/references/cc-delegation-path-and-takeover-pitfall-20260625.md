# CC 委派路径纠偏与接管边界（2026-06-25）

## 触发场景

一次 AI-MUD 文档修改任务中，delegator 让 CC 根据审计报告改 Obsidian 项目文档。失败链条不是“CC 不可信”这么简单，而是 delegator 的委派包与监控不够硬：

1. 首轮准备了 context 但没有真正启动 CC。
2. 后续 CC 被要求改文档，但路径约束不够硬，读到了同名/相似的错误目录。
3. delegator 只看“CC 在读文件/思考”，没有第一时间验证读取路径和目标文件 mtime。
4. CC 卡住后，delegator 直接接管写文件，违背了用户“让 CC 修改”的明确工作流偏好。
5. 用户纠正：**“cc 不可信也是因为你指挥的问题”**，不要把编排失败甩给执行 agent。

## 持久教训

### 1. 先审委派包，再怀疑执行方

当 CC 走偏、卡住或读错文件时，第一反应应是检查 delegator 是否给了足够清晰的约束：

- 是否给了唯一绝对路径？
- 是否禁止了 Glob/Search 去找同名目录？
- 是否指定了工作目录？
- 是否明确禁止修改相似/旧目录？
- 是否要求每次写入报告绝对路径？
- 是否在首轮抓屏里核对了 CC 实际读取的路径？

不要笼统总结为“CC 不可信”。更准确的判断通常是：**委派包不够硬 + 监控没有验证关键证据**。

### 2. 路径敏感任务必须做“首读路径验收”

在有多个相似项目目录、Obsidian vault、monorepo、多 profile 或迁移残留时，CC 发任务后第一轮必须检查：

```text
✅ CC 实际读取的文件路径是否等于委派包中的绝对路径
✅ 目标文件 mtime 是否只在正确目录变化
✅ 没有读取/写入禁止目录
```

如果发现读错目录，立即 C-c 或纠偏，不要继续等待。

### 3. 用户指定“让 CC 改”时，Hermes 不得擅自接管写入

如果 CC 卡住或走偏，允许做的是：

1. 停止/暂停 CC；
2. 向用户报告真实状态；
3. 修正委派包；
4. 重启或继续 CC；
5. 必要时让用户选择“是否改由 Hermes 接管”。

**不允许**在没有用户明确同意的情况下，Hermes 自己直接写目标文件，尤其是用户已经明确要求“让 CC 直接修改”的场景。

### 4. 汇报承诺要和机制绑定

如果对用户承诺“每 2-3 分钟报进度”，就不能只挂 notify_on_complete 后结束 turn。要么：

- 用 in-turn wait 循环，每轮 wait 超时后抓屏 + 报告；
- 要么明确告诉用户“我会在完成通知后回来”，不要承诺持续进度。

## 推荐委派包片段

```text
唯一工作目录：<absolute project path>
禁止使用 Glob/Search 去找项目目录。
禁止读取/修改：<known wrong path 1>, <known wrong path 2>
只允许修改以下绝对路径：...
每改完一个文件，报告：已写入：<absolute path>
首个动作：读取第一个目标文件，并在回复中显示读取的绝对路径。
不要问问题，直接执行；遇到路径冲突立即停止并报告。
```
