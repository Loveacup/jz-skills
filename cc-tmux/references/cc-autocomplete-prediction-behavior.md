# CC Autocomplete / Prediction Behavior

> 2026-06-30 · Alex 亲自纠正 · v1.40.0 核心设计依据

## Alex 的原话

> "关于这个 CC 输入框里的残留文字，其实是它在预测下一次是否按照这个内容进行输入，相当于自动补全。作为我来操作的时候，如果我按一个 Tab 键，它就会把这个文字复现出来；然后我再回车，它就直接把我猜测的补全内容输入进去了。所以它其实不是残留文字。"

> "这个'补全'的对话需要纳入你的考量：是否要执行 CC 的下一步意见？而不是很单纯地就把这个归为一个残留信息，然后就直接不管它了。"

## 行为解释

CC 的 TUI 有一个类似 shell 自动补全的功能：基于当前对话上下文，预测用户下一步可能想输入什么。这个预测以 ghost/dim 样式出现在 `❯` 提示符后面。

- **Tab 键**：把预测文本填充为真实输入
- **Enter 键**：直接执行预测内容

## 为什么要区分

在 v1.38/v1.39 中，所有 `❯` 后的文字都被归为 "residual"，这导致了两个问题：

1. **误判**：把 CC 的正确预测当成"输入框残留"，可能执行不必要的清理或重发
2. **错失机会**：CC 的补全通常是合理建议（如"继续执行 /tmp/cc-task.md"），盲目清除等于浪费 CC 的推理成果

## 当前处理策略（v1.40.0）

因为 `tmux capture-pane` 无法看到 ghost/dim 属性（TUI 层面的文本样式不被终端协议保留），我们无法在 pane 级区分"残留"和"补全"。因此 v1.40.0 采用了**上下文判定**而非**样式判定**：

### 分类模型

| 场景 | 判断条件 | 分类 | 行动 |
|---|---|---|---|
| 刚发送 `send-keys "按 /tmp/task.md 执行" Enter`，立即回读 pane 看到 `❯ 按 /tmp/task.md 执行` | 文本 == 刚发消息 | `fresh_sent_line` | 可安全 Enter（在修复窗口内） |
| CC 已完成上一轮并 IDLE，pane 显示 `❯ read /tmp/report.md` | 没有近期 send-keys，文本是任务延续 | `prediction_candidate` | **不 Enter**，作为建议呈现给 Hermes |
| CC IDLE 但 pane 显示几轮前的旧指令 | 文本跨轮次未清除 | `stale_or_unknown` | `/clear` 后重发 |
| `❯` 后没有任何文字 | 干净的空提示符 | `idle_empty` | 安全发送下一条指令 |

### 关键原则

- **永远不自动 Enter 未知文本**
- **永远不自动 Enter 补全候选**
- **预测文本是建议，不是命令**——Hermes 可以读取并评估，但不能盲目执行

## 如果未来技术允许

如果 Claude Code 未来在 hook JSON 或 status 文件中暴露 `autocomplete_text` 或类似字段，我们可以切换到样式判定而非上下文判定。在此之前，分类模型依赖"刚发了什么"这个唯一可证事实。

## 与 `cc-stuck-input-box-pattern.md` 的关系

本文件补充分类模型的**理论依据**（为什么补全 ≠ 残留），而 `cc-stuck-input-box-pattern.md` 偏向**操作流程**（怎么清理、怎么重发）。二者互不替代。
