## 一、分级定义

| 级别 | 名称 | 判定标准（满足任一即归入） | 处理路径 |
|------|------|---------------------------|---------|
| **L0 — 简务** | 单点直批 | 单点查证、事实确认、配置读取、已知固定链路（如早新闻） | 太子直批，不输出 plan-preview，直接派工 |
| **L1 — 轻量规格** | 轻量规划 | 单步骤但有明确验收标准、无跨领域、无视觉交付、无多轮验收风险 | 中书省输出轻量规格（≤10 行），不经门下省封驳，直接派工 |
| **L2 — 繁务** | 完整进奏 | 多执行步骤、跨领域（>1 skill 域）、视觉交付（HTML/图片/视频）、多轮验收可能、制度/架构修改 | 中书省输出完整 plan-preview → 门下省封驳 → 尚书省派工 |
| **L3 — 御批** | 父皇裁决 | 需求歧义、风格取舍、验收口径冲突、无历史先例、预算/超时超出常规、返修/恢复超限 | 建 blocked decision card，请父皇定夺 |

## 二、判定条件详细说明

### L0 — 简务（单点直批）

**必须同时满足：**
1. 任务可被单一工具调用完成（如一次 `web_search`、`read_file`、`terminal`）
2. 无需多文件/多步骤协调
3. 结果可即时验证（如返回配置值、搜索结果、文件内容）
4. 无外部副作用或副作用可控（只读或本地非持久操作）

**典型示例：**
- "查一下当前 Hermes 版本"
- "读取 ~/.hermes/config.yaml 第 100-120 行"
- "搜索某股票的当前价格"
- "早新闻"（已知固定链路：三路检索→汇总→推送）

**禁止归入 L0 的情形：**
- 涉及文件写入、配置修改、代码变更
- 需要跨多个目录/系统收集信息
- 需要判断/分析/综合（非纯查证）

### L1 — 轻量规格（轻量规划）

**必须同时满足：**
1. 单步骤执行（一个执行节点完成）
2. 有明确、可量化的验收标准（如"输出 X 文件到 Y 路径"）
3. 不跨领域（只涉及一个 skill 域或基础工具）
4. 无视觉交付要求
5. 无多轮验收风险（一次完成即终稿）

**典型示例：**
- "创建一个 cron job，每早 8 点运行某脚本"
- "将某 skill 更新到最新版本"
- "修复某配置文件的拼写错误"

**处理流程：**
```
用户指令 → 中书省输出轻量规格（≤10 行）→ 尚书省派工 → 执行 → 验收
```

**轻量规格格式：**
```markdown
目标: [一句话]
输入: [已有资源]
输出: [预期产物]
验收: [可量化标准]
超时: [预估时间]
```

### L2 — 繁务（完整进奏）

**满足任一即归入：**
1. **多执行节点**：任务含 ≥2 个执行步骤，或需要 fan-out/fan-in
2. **跨领域**：涉及 >1 个 skill 域（如同时涉及 `github` + `web` + `terminal`）
3. **视觉交付**：输出包含 HTML、图片、视频、PPT 等视觉产物
4. **多轮验收可能**：存在 review→修改→再 review 的循环风险
5. **制度/架构修改**：修改 governance skill、SOUL.md、权限矩阵、A2A 规范等
6. **复杂评估**：需要比较多个方案、技术可行性不确定（spike 场景）

**典型示例：**
- "设计一个新的 governance skill"
- "重构某系统的架构，需要比较 3 个方案"
- "创建一个多步骤的数据处理流水线"
- "修改三省六部制度文件"

**处理流程：**
```
用户指令 → 中书省 plan-preview（含任务图、验收标准、风险点、决策项）
  → 门下省封驳（审目标/范围/预算/验收标准）
  → 门下省通过 → 尚书省派工（fan-out/fan-in）
  → 执行 → 门下省复核（对照验收标准）
  → 御史台稽核 → 史馆归档
```

### L3 — 御批（父皇裁决）

**满足任一即归入：**
1. **需求歧义**：用户意图不明确，多种理解可能
2. **风格取舍**：视觉/表达风格无历史先例，需用户确认
3. **验收口径冲突**：多个验收标准互相矛盾
4. **无历史先例**：该类型任务首次出现，无过往样本参考
5. **预算/超时超出常规**：超出该 profile 常规预算范围
6. **返修/恢复超限**：同一任务返修 >2 次或恢复 >2 次

**处理流程：**
```
检测到 L3 条件 → 建 blocked decision card
  → 父皇裁决（选择/确认/驳回）
  → 中书省根据裁决继续拟制或调整分级
```

**Decision Card 格式：**
```yaml
question: "具体问题描述"
options:
  A: "选项A描述"
  B: "选项B描述"
  C: "选项C描述（如适用）"
recommendation: "中书省推荐选项及理由"
timeout_default: "2min"
impact: "选择不同选项对任务的影响"
```

## 三、快速判定决策树

```
用户指令
  │
  ├─→ 单点查证/配置读取/已知固定链路？
  │     ├─→ YES → L0 简务（直批）
  │     └─→ NO
  │
  ├─→ 需求歧义/风格取舍/无先例/预算超限？
  │     ├─→ YES → L3 御批（Decision Card）
  │     └─→ NO
  │
  ├─→ 单步骤 + 明确验收 + 无跨领域 + 无视觉 + 无多轮风险？
  │     ├─→ YES → L1 轻量规格
  │     └─→ NO
  │
  └─→ L2 繁务（完整 plan-preview）
```

## 五、降级与升级规则

| 场景 | 动作 | 触发条件 |
|------|------|---------|
| **降级** | L2 → L1 或 L1 → L0 | 任务实际执行中发现比预期简单，经太子确认后降级 |
| **升级** | L0/L1 → L2 | 执行中发现复杂度超预期，或涉及未预见的跨领域/视觉交付 |
| **返修超限升级** | 任意 → L3 | 同一任务返修 >2 次 |
| **恢复超限升级** | 任意 → L3 | 同一任务恢复 >2 次 |
| **预算超限升级** | 任意 → L3 | 实际耗时/成本超出 plan 预估 50% 以上 |

**降级/升级必须记录：**
- 原分级、新分级、变更原因、变更时间、变更人（profile）
- 记录位置：任务 comment 或 handoff_schema metadata

## 六、角色职责对照

| 角色 | L0 简务 | L1 轻量规格 | L2 繁务 | L3 御批 |
|------|---------|------------|---------|--------|
| **太子/Regent** | 直批派工 | 审规格后派工 | 启动 plan-preview 流程 | 呈报 Decision Card |
| **中书省/Planner** | 不参与 | 输出轻量规格 | 输出完整 plan-preview | 拟制 Decision Card |
| **门下省/Reviewer** | 不参与 | 不参与 | 封驳 plan + 复核结果 | 不参与（父皇直裁） |
| **尚书省/Dispatcher** | 直接派工 | 直接派工 | 按任务图 fan-out/fan-in | 等待父皇裁决后派工 |

## 七、验收标准

1. **路由准确率 ≥90%**：用 P0/P0.5/P1 历史任务做回归测试，判断与实际处理一致
2. **决策卡触发率 100%**：所有 L3 条件任务必须建 Decision Card，不得擅断
3. **降级/升级记录率 100%**：所有分级变更必须有记录
4. **L0 误判率 ≤5%**：实际为 L2 但被误判为 L0 的任务比例不超过 5%
5. **L2 漏判率 ≤5%**：实际为 L2 但被误判为 L1/L0 的任务比例不超过 5%
