# Pi Grill — 设计拷打

一次一个问题，逐层深挖，直到所有分支都探索完毕。

---

## 🚨 Red Flags: 拷打前自查

| 你会想 | 为什么不对 |
|--------|-----------|
| "方案很明显，不需要拷打" | 最明显的方案藏着最危险的假设 |
| "我把问题列一条消息里就行" | 批量=用户只回最后一个。逐个来 |
| "用户很忙，快点结束" | 匆忙的拷打不如不拷打 |
| "这个问题用户肯定知道" | 先读代码/文档确认。如果代码能回答就别问 |

**如果你冒出了上面的念头 → 停下来，按下面流程一步步走。**

---

## 🔀 拷打流程

### Phase 1: 理解方案

1. 读取用户提供的文档、代码、上下文
2. 识别核心决策树 — 有哪些分支需要探索？
3. 找到最根本的假设（根节点）

### Phase 2: 深度优先遍历

4. **从根节点开始** — 一次只问一个问题
5. **附带建议** — 每个问题带上你的推荐答案
6. **解决后再下钻** — 不跳到下一个分支，直到当前分支完全解决
7. **碰壁回溯** — 分支不通就回到上一级，找下一个开口

### Phase 3: 证据挑战

8. **读代码/文档验证** — 用户说"某功能是这样" → 去看代码。发现矛盾 → 立刻提出
9. **模糊语言精确化** — "高可用"→ "几个9？RTO多少？"

### Phase 4: 收尾

10. **追踪已决策项** — 防止兜圈子
11. **知道何时停** — 全分支解决 或 用户喊停。不死缠烂打
12. **总结** — 所有决策 + 未决问题 + 下一步建议

## 示例对话流程

```
Agent:  方案的核心假设是"先做单机版再扩展分布式"。为什么不是一开始就分布式？
        建议：单机原型验证快，但后期迁移成本高。

User:   单机够用，团队只有2个人。

Agent:  那数据量预期呢？如果半年内单机扛不住，到时候有迁移方案吗？
        [不跳到"用什么数据库"，先解决数据量问题]

User:   预计日增百万条，用 PostgreSQL 应该能撑一年。

Agent:  ⚠️ 我看了项目里现在的 schema，没有分区表设计。百万日增=3.6亿/年，
        PG单表到这个量级查询会崩。要不要现在加分区？还是接受一年后重构？

...
```

## Pitfalls

- 批量提问 — 用户只回答最后一个，前面的白问
- 忽略代码证据 — 能读代码验证的却开口问
- 浅层拷打 — 只问"为什么用 X 技术"，不追问"X 技术的这个具体场景下能撑住吗"
- 死缠烂打 — 用户喊停还继续
- 没有总结 — 拷打完不留决策记录等于白拷

## 验证清单

- [ ] 每次只问一个问题（非批量）
- [ ] 每个分支完全解决才进入下一个
- [ ] 优先读代码/文档而不是提问
- [ ] 模糊术语被精确化挑战
- [ ] 结尾输出决策总结 + 未决问题 + 下一步
