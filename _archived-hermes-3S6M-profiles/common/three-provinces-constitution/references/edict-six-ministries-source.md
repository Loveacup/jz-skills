## edict 六部总览

edict 的六部按「做什么」分，每个都有明确的任务触发场景——这是 Hermes 当前最缺的：

| 部 | edict 职责 | Hermes 空转原因 |
|----|-----------|----------------|
| 兵部 | 代码实现（功能开发、架构、重构） | engineer 在用，但兼管基建 |
| 工部 | 基础设施（部署、监控、安全） | **缺口**，engineer 兼管 |
| 户部 | 数据分析（统计、报表、成本） | budget 无实际数据任务 |
| 礼部 | 文档编制（README、规范、排版） | protocol 无实际文档任务 |
| 刑部 | 测试审查（code review、测试、合规） | security+tester 空转 |
| 吏部 | Agent管理（接入、培训、考核） | registry 空转 |

## edict 尚书省派发机制

```
# 尚书省 · 执行调度

## 确定对应部门

| 部门 | agent_id | 职责 |
|------|----------|------|
| 工部 | gongbu | 开发/架构/代码      |  ← 注：此处与工部自身 SOUL.md 不一致
| 兵部 | bingbu | 基础设施/部署/安全   |  ← 注：此处与兵部自身 SOUL.md 不一致
| 户部 | hubu | 数据分析/报表/成本 |
| 礼部 | libu | 文档/UI/对外沟通   |
| 刑部 | xingbu | 审查/测试/合规     |
| 吏部 | libu_hr | 人事/Agent管理/培训 |

## 调用六部 subagent 执行
对每个需要执行的部门，**调用其 subagent**，发送任务令：
📮 尚书省·任务令
任务ID: JJC-xxx
任务: [具体内容]
输出要求: [格式/标准]

## 汇总返回
收集六部结果 → 状态转为 Review → 回调中书省转报皇上
```

> ⚠️ 尚书省 dispatch table 中工部/兵部职责与各自 SOUL.md 互换了——这是 edict 的一个已知 bug。正确映射应以各部 SOUL.md 为准：兵部=代码，工部=基础设施。

## 对 Hermes 的启示

1. **edict 六部是「动词驱动」**：每个部绑定具体任务类型（写代码→兵部 / 管服务器→工部 / 搜数据→户部），Hermes 的「名词驱动」（预算/协议/安全/资粮）导致无触发场景
2. **尚书省是真正的 dispatch hub**：手持 capability 表做匹配派发，Hermes 尚书省从未履行此职
3. **状态机有代码层硬校验**：kanban_update.py 内置 VALID_TRANSITIONS，非法跳转拒绝——Hermes 全靠 agent 自觉
4. **实时进展上报是必做项**：每个部在关键步骤调用 progress 命令——Hermes 只有 post-hoc 审计

## 提取技术笔记

GitHub raw.githubusercontent.com 页面在 browser 工具中常渲染为空（element_count=0），但实际 DOM 已加载。workaround：
```javascript
// browser_console
document.body.innerText
```
可获取完整文件内容。此模式适用于所有 raw.githubusercontent.com 路径。
