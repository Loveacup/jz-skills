# Supermemory API Quirks & Limitations

> Discovered 2026-05-29 during multi-profile cabinet memory deployment and regent architecture testing.
> These are Supermemory **platform** behaviors, not Hermes bugs.

---

## §G4: Search Index Gap (Critical Platform Bug)

**Symptom**: Documents reach `status=done` (t≈10s) but NEVER appear in `search.memories()` results, even at t=60s+.

**Verified**: Yes — 2026-05-29, three independent test runs.

**Reproduction recipe**:

```python
client = Client(api_key=key)

# 1. Write
r = client.add(content="G4-TEST: unique content string", container_tag="hermes-cabinet")
doc_id = r.id

# 2. Poll status every 5s
for t in [0, 5, 10, 15, 20, 30, 45, 60]:
    doc = client.documents.get(doc_id)
    sr = client.search.memories(q="G4-TEST", container_tag="hermes-cabinet", limit=5)
    in_results = any(getattr(it, 'id', '') == doc_id for it in sr.results)
    print(f"t={t}s: status={doc.status} in_search={in_results}")
```

**Observed results (2026-05-29)**:

| t | status | content in `get()` | in `search.memories()` |
|---|--------|-------------------|----------------------|
| 0s | queued | ✅ | ❌ |
| 5s | indexing | ✅ | ❌ |
| 10s | **done** | ✅ | ❌ |
| 15s | done | ✅ | ❌ |
| 20s | done | ✅ | ❌ |
| 30s | done | ✅ | ❌ |
| 45s | done | ✅ | ❌ |
| 60s | done | ✅ | ❌ |

**Document status pipeline**: `queued → extracting → chunking → embedding → indexing → done`
- `dreaming_status` is separate from main `status` — can be `done` while `status` is still `queued`
- `status=done` means document processed, NOT that it's indexed into the search vector DB

**Impact**: Design doc v2.0's entire write→recall loop is broken. Documents stored but invisible to search means agent write is effectively a no-op from the agent's perspective.

**Workaround**: None on our side. This is a Supermemory platform bug requiring their engineering team.

**Mitigation**: 
- Use `documents.get(id)` for direct retrieval instead of `search.memories()` for new writes
- Retry `search.memories()` with exponential backoff (1s, 2s, 4s, 8s, 16s, 32s) before giving up
- Log search misses to detect patterns

## §Metadata: Custom Metadata Stripped from Search Results

**Symptom**: Custom metadata passed to `client.add(metadata={...})` is stored but stripped from `search.memories()` results.

**Verified**: Yes — 2026-05-29.

**Reproduction**:

```python
r = client.add(
    content="test content",
    container_tag="hermes-cabinet",
    metadata={"department": "debug", "type": "test", "visibility": "cabinet-shared"}
)

# Direct get — metadata IS here
doc = client.documents.get(r.id)
print(doc.metadata)  # {'department': 'debug', 'type': 'test', 'visibility': 'cabinet-shared'} ✅

# Search — metadata stripped
results = client.search.memories(q="test content", container_tag="hermes-cabinet", limit=5)
for item in results.memories:
    print(item.metadata)  # {'temporalContext': {...}}  — ONLY auto-generated temporalContext ❌
```

**What search returns**: Only `temporalContext` (auto-generated by Supermemory's NLP pipeline — contains `documentDate`, `eventDate`). All custom fields (`department`, `type`, `visibility`, `source`, `confidence`, `ttl`, etc.) are present in `documents.get()` but absent from `search.memories()`.

**Impact**: Design doc §5.3 (department-grouped rendering), §5.4 (metadata-driven template), §6 (visibility-based filtering), and §3 (full metadata schema) are all impossible with the current API. The entire "按部门分组呈现" design collapses without metadata in search results.

**Workaround**: Embed metadata as plain-text tags in `content`:
```python
content = "[dept:gongbu] [type:decision] [vis:cabinet-shared] 实际内容..."
```
This makes metadata searchable via full-text matching (which `search.memories()` does support) but loses structured filtering.

**Note**: `documents.get(id)` DOES return custom metadata. This means metadata is stored correctly — it's a search-index limitation, not a storage limitation.

## §SDK: Parameter Name Quirks

### `client.add()` — uses `container_tags` (plural, list)

```python
# ❌ Wrong
client.add(content="x", container_tag="hermes-cabinet")

# ✅ Correct
client.add(content="x", container_tags=["hermes-cabinet"])
```

### `client.search.memories()` — uses `q=`, not `query=`

```python
# ❌ Wrong
client.search.memories(query="search text", container_tag="hermes-cabinet")

# ✅ Correct
client.search.memories(q="search text", container_tag="hermes-cabinet")
```

### `AddResponse` is a Pydantic model, not a dict

```python
r = client.add(content="x", container_tags=["hermes-cabinet"])
# r is AddResponse(id='...', status='queued')
doc_id = r.id      # ✅ attribute access
# doc_id = r["id"]  # ❌ TypeError — not a dict
```

### Return types

| Method | Return type | Key attributes |
|--------|------------|----------------|
| `client.add()` | `AddResponse` | `.id`, `.status` |
| `client.documents.get(id)` | `DocumentGetResponse` | `.id`, `.status`, `.dreaming_status`, `.content`, `.metadata` |
| `client.search.memories()` | `SearchMemoriesResponse` | `.results` — list of items with `.id`, `.memory` (content), `.similarity`, `.metadata` |
| `client.profile.get()` | `ProfileGetResponse` | `.static_count`, `.dynamic_count`, `.recent_context` |

## §Document Status States

Full pipeline (observed, not all documented by Supermemory):

```
queued → extracting → chunking → embedding → indexing → done
```

- `dreaming_status` is independent from `status`. A document can have `dreaming_status=done` while `status=queued`.
- `status=done` does NOT mean the document is in the search index (see §G4 above).
- `status=failed` — not yet observed but exists in the SDK type definition.

## §Profile: static_count Behavior

- `static_count` increases when Supermemory detects repeated patterns across enough documents to solidify into a "profile fact"
- Threshold is `profile_frequency` (likely 50 in Supermemory's config)
- `dynamic_count` is the running total of dynamic context items
- Cabinet pool has too little traffic for `static_count` to trigger — this is normal, not a bug
- If multi-agent profiles need permanent profile facts, they need to be written explicitly as `type: user_profile` memories

## §Cross-Profile Write Guard

When profile A's agent tries to write to profile B's files (e.g., regent patching default's files):

```
Cross-profile write blocked
```

**Workaround**: 
1. Run from the target profile
2. Use terminal with explicit path
3. Use shared location

This is by design — a security feature, not a bug.

## Summary: What the Design Doc Assumes vs Reality

| Design doc § | Assumption | Reality | Status |
|-------------|-----------|---------|--------|
| §5.3 | Search returns `department` for grouping | Only `temporalContext` returned | ❌ Broken |
| §5.4 | `m.metadata["type"]` available | Not available in search | ❌ Broken |
| §6 | `visibility` filterable in search | Not filterable | ❌ Broken |
| §3 | Metadata taxonomy enforceable | Only on write side; invisible on recall | 🟡 Partial |
| §13.2 | Search returns full memory objects | Search returns truncated objects without custom metadata | 🟡 Partial |
| G4 | Write→index pipeline is reliable | Pipeline broken; done ≠ searchable | ❌ Broken |

**Bottom line**: Until Supermemory fixes these two issues (search index gap + metadata in search results), the cabinet memory architecture operates at ~50% of design intent. Write+direct-get works. Semantic recall with metadata-driven filtering does NOT.
