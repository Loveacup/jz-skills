# agent-coord：统一工作协调入口

> **状态标注**：STDD Build 产出，已于 2026-09-17 通过 spec-001 A1–A10 文档验收。本文是「上层选择」入口，**非默认入口**，也不为任何实施、Git 写入或通道操作授权；默认入口切换属 P6，另行批准。

## 0. 定位与硬边界

- 本 skill 只承载「上层选择」：工作方法 → 角色与配方 → 控制通道 → 工作区与授权。
- **不含**任何通道的操作命令教程。启动、消息、问答、停止、恢复、清理等操作细节，一律以对应通道 skill／原生随版本文档的**现行版本**为准；本文与通道文档冲突时，以通道现行版本为准。
- 本 skill 不常驻运行、不轮询、不加锁、不维护任务状态库、不镜像运行状态；运行状态每次从所选通道原生回读，本层只记录原生定位指针与证据引用。
- 配方是给 Hermes 的判断提示，不是可执行 DAG 或调度状态机。

## 1. 何时启用 / 不启用

**不启用（默认优先）**：简单、小范围、Hermes 单人能闭环的任务直接做，不组队、不走配方路由。增加任何角色都必须能解释收益来自以下之一：信息覆盖、独立产出、上下文分离、独立验证；「有多个模型/CLI 可用」不是理由。

**启用**：任务涉及多交付物分工、真实并行覆盖、需要独立审核、跨通道派工，或需要在多个控制通道之间做选择时。

## 2. 通用判断顺序

按顺序推演，每步有明确答案再进下一步；这是方法建议，不是额外审批门。

1. **定义可验收结果**：目标、不可变约束、授权对象、证据标准、何时算完成。
2. **判断是否值得组队**：单人能闭环则不组队（见上节）。
3. **盘点现有输入**：已有成果、专业 skill、证据；不重复探索已有答案的问题。
4. **按交付物拆分**：每份产物一个负责者；先拆交付物，再拆角色。
5. **识别依赖与共享写面**：真实依赖才串行；共享写面（含 lockfile、构建产物）须隔离或串行。
6. **选择最小配方**：按第 3 节路由表选 F1–F6，并说明选择理由。
7. **选 CLI 与通道**：按任务相关能力与准入证据选择，见第 4 节；不按品牌偏好硬绑定。
8. **绑定工作区与授权**：见第 5 节；四类所有权分别记载。
9. **执行与反馈**：按所选通道观察；进度查询只读取；用户补充按影响范围定向传递。
10. **独立验收与整合**：Hermes 对总验收负责；worker 自述不能替代验证。

## 3. 配方路由表

详细配方卡（七要素）与角色槽位见 `references/recipes-and-roles.md`。

| 任务特征 | 配方 |
|---|---|
| 目标清楚、小范围、低耦合 | F1 单执行闭环（或 Hermes 直接处理，不组队） |
| 后件确实需要前件产物 | F2 顺序接力 |
| 对象/维度独立、覆盖收益大 | F3 并行分面→综合 |
| 标准清楚、缺陷代价值得审查 | F4 产出→独审→定点修订 |
| 关键取舍存在合理不同路线 | F5 候选方案→证据裁决 |
| 子问题只能随调查展开 | F6 有界动态探索 |

组合方式：按阶段衔接配方而非复制 SOP，如诊断修复 F3→F1→F4、分区实现 F3→F2 集成→F4。

## 4. 通道选择路由

详见 `references/channel-selection.md`。核心原则：

- **一个业务任务同一时刻只有一个决策控制者；一次执行尝试只有一个生命周期控制通道。**
- 准入五维核对：原生支持、目标宿主安装、认证可用、实际投递/执行、产物与生命周期闭环；再按任务需要核对问答、停止、接续、证据、权限/资源限制。
- Orca 为「优先验证底座」，但非唯一通道；缺口标「未验证/受限」，不用文档承诺补齐。
- Hermes Kanban 派工必设 `--max-runtime`/`--max-retries`；运行中的卡不用 `block`，协调者也不用 `reclaim`：取消或换新 attempt 都先 `archive` 旧卡、停掉子执行、用 `ps` 取得停写证据，换新 attempt 再新建卡。细则见 channel-selection.md。
- 角色与 CLI/通道解耦：任何「角色 X 必须由品牌 Y 承担」的说法都不是本层规则。

## 5. 工作区与交接

详见 `references/workspace-and-handoff.md`。核心原则：

- 四类所有权分别记载：workspace owner / execution owner / Git writer / document owner；可由同一主体兼任，但**权限不隐式合并**。
- 工作区选择梯度：普通 folder → 共享只读 → 复用现有 checkout → 独立 worktree；按最小需要选择。
- 执行者不得私删不归自己所有的工作区；清理归 workspace owner。

## 6. 任务包与结果交接

- 派工用 `templates/task-package.md`：小任务一段即可，复杂任务才扩表；字段是上层文档约定，非任何原生 API 字段。
- 回收用 `templates/result-handoff.md`：文件承载成果，消息传递变化；先落盘产物再发引用。

## 7. 验收与收口 SOP 摘要

- 核对**实际产物、要求版本、freshness、范围、测试/证据**；代码任务另核源契约与集成后（目标版本上）重验。
- 生命周期 succeeded 可与业务 blocker/stale 并存，不改写原生事实；worker 完成消息只是交接，不等于业务验收。
- 结果不满足要求只派明确的定点返工，不重发整包；**讨论≤3 轮、退回≤2 次**仍不过则停止自动循环，升级裁决。
- 总完成要求：承诺项均有 verdict/证据、授权写入已回读、未决项明确、资源已结算或有明确保留理由、用户获得可访问结果。取消是合法终态，但不是业务完成。
