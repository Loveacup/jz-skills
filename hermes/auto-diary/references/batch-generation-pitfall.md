# 批量生成陷阱 v1.0

## 事件

用户要求"重写整个 5 月份的日记"，Agent 写了一个 Python 脚本批量生成 30 份日记。

## 用户反馈

> "不行啊，你批量生成的质量太垃圾了"

## 根因

批量生成的日记是模板填充：
- 三问直接从 `ai_logs.*.topics` dump 原始字符串（"work kanban task t_cf1c6c9b"），完全不可读
- Hermes 治理体系段落全是占位符，实际数据被忽略
- 每份日记 900-1200 字符，毫无叙事价值

## 正确做法

1. **逐天处理，不批量化**：每份日记独立走 LLM 加工，不允许 Python 循环 foreach write。
2. **三问必须有叙事**：三问不能只是 topic dump。必须读取 cron 输出摘要 + 原始 topic 数据 → LLM 理解当天发生了什么 → 写成可读叙事。
3. **数据先行**：每条日记重写前，必须 `collect_data.py` 重新拉取当天原始数据。不依赖之前扫描的摘要。
4. **节奏不决定质量**：用户说"逐条来吧"时，宁可慢、要对。为赶进度压缩质量是错的。
5. **零数据日合并**：Hermes/CC/vault/cal 全零的日不创建独立日记。连续多日 → 合并为一篇时期笔记。仅 CC /usage 的低密度日同理。
6. **保留用户内容**：如果已有日记存在（existing_content），必须读取并保留用户手写的三问、个人生活、待办等内容。
7. **叙事优先于数据密度**：轻量日（周末、治理日常为主）的日记可以精简，但要保证叙事完整性——不是字数越多越好，是信息密度和可读性的平衡。

## 质量自检

生成每份日记后，自问：
- 三问第一条的答案是否可读？是否有洞察？还是 dump？
- CC 部分是否按 🤝/💻/🤖 三组展示？数据与 `collect_data.py` 输出一致？
- Hermes 治理体系是否有实质内容？还是放了"九部全覆盖"就跑？
- 日历事件、个人生活、待办是否保留用户已写内容？
