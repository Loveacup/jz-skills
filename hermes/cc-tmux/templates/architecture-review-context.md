# CC 架构审查 context 模板

> 适用场景：让 CC 对自己或他人代码库做深度代码审查 + 架构评估。
> 4 层递进：代码验证 → 架构审计 → 优先级排序 → 产出方案。

## 模板

```markdown
# {项目名} 全面评估任务

## 你是什么
{一句话定位——CC 的角色和本次任务的上下文}

## 代码库位置
- 主代码库：`{canonical code path}`
- 运行时部署：`{deploy path}`
- PRD（需求权威）：`{path}`
- 架构设计：`{path}`

## 当前基线
{版本 · 测试数 · 健康分 · 已知负债}

## 已有审查结论（如有）
{上次审查产出路径 + 关键发现摘要}

## 你的任务（全面评估 → 输出可执行方案）

### 第一层：代码级验证
1. 通读所有核心文件（脚本 / hooks / templates / tests）
2. 验证 deploy 副本与源码一致性
3. 验证测试覆盖盲区
4. 检查接口契约漂移

### 第二层：架构审计
5. 对照需求文档逐条验证覆盖率
6. 检查架构原则是否全量落地（convention 改 gate）
7. 评估关键流程的保障机制
8. 检查事件链路完整性

### 第三层：改进优先级排序
9. 基于审查发现 + 已有结论 + 外部对比，排出改进优先级
10. 每个改进项评估：成本（高/中/低）× 杠杆（高/中/低）× 风险

### 第四层：产出
11. 结构化审查报告 → `{output path}`
12. 对 P0 项：直接写可应用 patch
13. 如果发现测试盲区：写明该补什么测试

## 约束
- 不改动不相关文件
- 不提交、不推送
- 遵守现有代码风格
- 遵守项目 AGENTS.md 工作约定
- 产出全是分析和建议，不改代码（留给审核方执行）

## 澄清指令
在开始执行前，请先复述你对任务的理解，包括：
- 你认为最关键的评估维度是什么
- 你打算分几步走
- 有没有不明确的点需要先澄清

确认理解后开始逐层评估。
```

## 使用方式

1. 复制模板，填充 `{...}` 占位符
2. 按需调整层数（简单项目可砍到 2 层）
3. 写入 `/tmp/cc-context-{topic}-{date}.md`
4. `cc-send.sh --session X --context /tmp/cc-context-...`
5. 三段协议：节点①等 CC 复述理解 → 对齐后开干 → 节点③审核产物

## 关键设计

- **4 层递进**：先查代码（客观）→ 再审架构（主观）→ 再排优先级（判断）→ 最后产出（可执行）
- **预置约束**：防 CC 跨过审核方直接改代码
- **澄清指令**：R2.1 澄清式交接模式，CC 先复述理解再动手
- **可复用**：把 `{...}` 换掉就是通用模板
