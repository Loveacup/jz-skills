# CC 审核交叉评判模式

> 来源：2026-06-16 用 CC 审核 regent 的路由方案三向交叉评判

## 模式

用 CC 审自己的设计时，CC 不会只说"对不对"，会挖出三类发现：

### 发现层级

| 层级 | 典型发现 | 本案例 |
|------|---------|--------|
| **L1 表面对齐** | 文档间矛盾、缺失字段 | 自动委派 vs 确认门控冲突 ✓ |
| **L2 纵向倒塌** | 深层设计缺陷（如审核者不独立） | 矛盾②：regent 设计 CC 方案 → regent 审核 CC 产物 = 人类控制点塌缩 |
| **L3 过度设计** | 四层方案建议最小切片先验证 | P1-P4 警告 ✓ |

### 常见误判（需人复核）

- **P2 被高估**：SOUL 已有半套 verifier（§工具输出审核），评审判"缺三元组"不够精确
- **P7 归错层**：溯源该放 cc-tmux/goal 层而非 SOUL，评判说"应在 SOUL 补"是过度设计
- **优点被当优点导出 bug**：审核→退回闭环没终止条件 → 导出给 goalgen 时连 bug 一起传

### 输出特征

CC 审核输出通常包含：
1. 可裁决的设计判断（同意/不同意 + 理由）
2. 遗漏项（"你没展开 P3/P8"）  
3. 可直接执行的修改建议（如 SOUL.md 重写版）
4. 需要人拍板的开放问题（"推不出，是你的事实/偏好"）

### 对 regent 的提示

给予 CC 审核任务时：
- 同时给出所有相关文档 + 设计决策背景
- 问具体问题（"这 6 个决策哪个站不住"），不要问"审核一下"
- CC 说"需要你拍板"的问题是真需要人的判断，不要让它自己裁定
