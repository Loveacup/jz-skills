# R2.1 澄清式交接协议（Clarification Protocol）

> **落地版本**：v1.20.0（协议 + 模板，零脚本）。**需求来源**：PRD `CC-TMUX核心需求.md` §5 R2.1。
> **一句话**：CC 接任务后、执行前多一个「澄清」阶段——**只读工具查证理解 → 形成方案 → 与 Hermes 讨论对齐 → 才执行**。
> **配套**：context 模板 `templates/r2.1-context-template.md`；简化版 `templates/discuss-first-snippet.md`；SKILL.md §3 三段协议节点①、§5.1 委派包。

---

## 1. 为什么需要

三段协议节点①（发任务前讨论）原版是「Hermes 等 CC 读完 context → 看 CC 怎么理解 → 偏了讨论纠正」。
但 CC 在那个停顿里**只是解读 Hermes 的文字**，不主动查证。结果：CC 的「理解」建立在 Hermes 单方面的简报上，
Hermes 简报里的盲点 = CC 的盲点。R2.1 的修法：**让 CC 在讨论前先调只读工具查证**，把理解建立在
查到的事实（代码、记忆、历史决策、知识库、联网背景）上，而不是字面转述上。

> 本质是 Matt Pocock「能查代码就查代码」原则的延伸——从「查代码」扩展到「查一切只读来源」。

---

## 2. 两侧职责

### A. Hermes 侧：首轮上下文富化

派发复杂任务时，用 `templates/r2.1-context-template.md` 填 6 段，而非写一段裸文字：

| Section | 填写原则 | 来源 |
|---------|---------|------|
| **1 任务简报** | 软引导不硬指定：「我理解你要做 X，关键看 Y，注意 Z」。留判断空间给 CC | Hermes 对 Alex 需求的理解 + 优先级 |
| **2 相关记忆** | 只摘**与本任务相关**的偏好/决策/陷阱，不堆全部记忆 | 本地 memory + SuperMemory |
| **3 知识库路标** | 给路标不搬全文：「相关内容在 X、Y、Z」 | OB vault（日记/项目/方案） |
| **4 Skill 建议** | 建议而非强制，附验收标准；CC 可澄清后推翻 | Hermes 本地 skill（+ CC 本地 / WRR） |
| **5 约束与红线** | 只放硬边界；验收契约（criterion）单列在委派包 | 已知不可触碰项 |
| **6 澄清指令** | 明确「先查证、再讨论、别直接执行」（见下） | 协议固定段 |

**填写纪律**：填不出的 section 直接删（别留空占位污染 CC 的注意力）。软引导原则——
不写「你必须用 A 方案」，写「Alex 之前偏好 X，OB 里有 Y 可参考，注意避开 Z」。CC 可推翻初始建议。

### B. CC 侧：澄清阶段（执行前）

```
Hermes 派发增强版 context（6 段）
  → CC 读任务简报（section 1-5）
  → CC 用只读工具查证（不写！）
    ├── WRR web-research-router  → 联网搜背景/技术方案/开源参考
    ├── SuperMemory + 本地 memory → Alex 历史决策/偏好
    ├── session_search           → 翻过往讨论
    ├── OB 知识库检索（含日记）   → 项目文档/方案/上下文
    ├── 本地 repo + CodeGraph    → 现有代码/架构/依赖
    └── 其他任何只读工具
  → CC 形成「我的理解 + 执行方案」
  → CC 发起讨论（grill 节奏，见 §4）
  → Hermes 判断 → 纠正 / 补充 / 确认
  → 达成共识 → 进入执行阶段（此后才能写文件/改代码）
```

## 3. 工具可用性清单（澄清阶段）

| 工具/能力 | 用途 | 权限 |
|----------|------|:--:|
| WRR `web-research-router` | 联网搜背景知识、技术方案、开源参考 | ✅ |
| OB 知识库检索 | 读日记、项目文档、过往方案、架构决策 | ✅ 只读 |
| Supermemory 记忆检索 | 跨 session 持久记忆 | ✅ |
| 本地 memory 检索 | Hermes 当前记忆 | ✅ |
| `session_search` 历史会话 | 翻之前的讨论 | ✅ |
| 本地代码/文件读取 | 项目代码、配置 | ✅ 只读 |
| CodeGraph | 符号索引、依赖分析 | ✅ |
| **写文件 / 改代码** | — | 🚫 澄清阶段禁止 |

> **关键规则**：澄清阶段 CC **只能读、不能写**。所有工具调用都为「理解」而非「执行」。
> 进入执行阶段后才能写文件、改代码。**靠 convention 自觉遵守，不靠 hook/脚本强制**（同节点①、Pitfall #8）。

## 4. 讨论格式（grill 适配）

澄清完成后，CC 向 Hermes 发起讨论。沿用 cc-tmux 的 📡 块格式，内容遵循 grill 三原则：

1. **逐问 + 带推荐答案**：每个不确定点列出来，**附 CC 自己的推荐答案**，不是开放式甩问题。
   「Z 点我倾向 A（理由…），也可以 B，请拍板」。
2. **查证优先于提问**：能通过工具查到的，**先查再说**——不把「我没查就不知道」当问题抛回来。
3. **矛盾立即指出**：查到的事实与 Hermes 简报/已有声明矛盾时，**当场点出**，可反向拷问 Hermes：
   「你说的 X，我在代码/记忆里查到的是 Y，哪个对？」

讨论结构（CC 输出）：
```
📡 澄清·我的理解与方案
  · 理解：<2-4 句，目标/产物/约束>
  · 查证结果：<工具查到的关键事实，含与简报的出入>
  · 方案：<打算怎么做>
  · 待拍板：① <点 + 推荐答案>  ② <点 + 推荐答案>
```

## 5. 与 in-turn wait 三段协议的集成

R2.1 是**节点①（发任务前讨论）的增强**，不改三段协议骨架：

| 节点 | 原版（v1.13.0） | R2.1 增强（v1.20.0） |
|------|---------------|---------------------|
| ① 发前讨论 | Hermes 等 CC 读完 → 看理解 → 偏了讨论 | **CC 先调只读工具查证** → 基于事实形成理解 → grill 节奏讨论 |
| ② 中间汇报 | wait 超时 → 抓屏 → 📡 汇报状态判断 | 不变 |
| ③ 完成后讨论 | turn-done → 读产物 → 讨论达标/遗漏 | 不变 |

操作上：Hermes 用 R2.1 模板写 context → `cc-send` → `cc-wait-marker.sh`（fswatch 事件驱动）等 CC 澄清产出 →
读 CC 的澄清讨论 → 对齐/纠正 → 再 `cc-send` 一条「确认，开始执行」（带委派包 criterion）。
澄清这一轮也吃 in-turn wait 的一个 wait 周期。

## 6. 何时用 / 何时跳过

| 任务类型 | 用什么 |
|---------|--------|
| 复杂任务（多文件、架构、调研、有歧义、高风险） | **完整 R2.1 模板**（6 段）+ 澄清阶段 |
| 简单/机械任务（单点修改、明确无歧义） | 简化版 `discuss-first-snippet.md`（只复述、不调工具）或直接发 |
| 决策树判定无需讨论的琐碎任务 | 跳过，直接发 + criterion |

> 用哪个是 Hermes 的判断（同三段协议决策树）。重模板套在琐碎任务上 = 浪费往返。
