# Evaluate a Skill

Use this resource to diagnose a problem or decide whether a substantive change helps. Choose evidence that resolves the actual question; ordinary wording edits follow the root's fast path.

## Define the claim

Start with the result the user needs and the observation that would decide it. Useful distinctions are artifact integrity, discovery, guidance adoption, task success and runtime/release state. A readable file does not prove discovery; loading does not prove benefit; a good result does not show which guidance caused it.

Inspect the produced artifact and relevant trace rather than the author's confidence. Length, checklist completeness and a model's self-score are not substitutes for task quality.

## Diagnose before rewriting

Ask what actually prevented the result:

- Not exposed or not selected: investigate the consumer's discovery surface and description.
- Relevant guidance omitted: reduce competition or put the information at the decision it supports.
- Conflicting interpretations: clarify the implicated contract or responsibility.
- Missing or incorrect knowledge/interface: repair that knowledge or interface.
- Sound guidance not followed in this run: distinguish an execution lapse from a text defect.
- Tool, permission or environment unavailable: address that capability boundary; prose cannot supply it.

These explanations can coexist. Use files, traces, source inspection or targeted research to distinguish them. Preserve counterevidence and leave untested explanations as hypotheses. The remedy may be less guidance, a better resource, an executable fix or no skill change at all.

## Choose proportional evidence

For discovery changes, try ordinary in-scope and adjacent out-of-scope requests using only the exposed names and descriptions. If competition or truncation matters, use the real catalog. A simulated selector is useful but does not establish actual consumer behavior.

For instruction changes, exercise a realistic task and inspect its output. Look for informed adaptation as well as compliance: can the agent retrieve a missing fact, recover when a recommendation fails, and preserve the user's requirements? Unnecessary research, repeated confirmation and mechanical steps are regressions too. A required process remains part of acceptance even if a different path produces a superficially correct result.

For scripts and schemas, invoke the actual interface with meaningful inputs. For moved references, resolve links and exercise the loading branch. For a runtime claim, observe the named consumer's real loader and task path. For crossing artifacts, use [Privacy](privacy.md). Reuse unaffected evidence and retain project-required checks; expand testing for a new failure, change or unresolved risk, not for ceremony.

## Compare a genuine baseline when comparison matters

Freeze the versions used and give independent runs the same task, inputs, authorization, consumer and material environment. Judge their artifacts against the same acceptance criteria. If a factor changed besides the skill, state the attribution limit. When both satisfy a criterion, report preserved behavior rather than inventing improvement.

A no-skill arm is useful when the question is added value. Keep host safety and user requirements identical across arms. Distinguish capability gain from fidelity to a workflow or preference; equal correctness alone is not retirement authorization. Measure time, tokens or unnecessary work when efficiency is actually part of the claim, rather than inferring runtime savings from file size.

For repeated tuning or a generalization claim, reserve realistic cases outside the tuning loop. Keep instance answers and verifier secrets out of the skill. Use additional independent trials to resolve meaningful uncertainty, and blind version labels for subjective comparisons when feasible. Report variation and coverage; no fixed case quota or universal score is needed.

## Refactor without losing capability

For a structural change, start from the skill's existing requirements wherever they live, then account for current knowledge, interfaces, constraints, callers and resources. Keep each capability in a place the relevant task can actually reach; when a live rule is not covered by the recorded baseline, inspect its actual purpose before deciding whether to preserve, clarify or remove it within authorization. Do not create a requirements file merely to run this comparison. Historical evidence can remain background without its old procedure becoming current again. An explicit before/after capability map is useful when loss or cross-owner movement is a real risk, not as a mandatory report for every edit.

## Executable trust boundaries

For skills that wrap mutation, shell execution, asynchronous agents or cleanup, verify the boundary rather than relying on prompt language:

- Exercise accepted modes and required values, including semantically blank input and empty members.
- Validate identifiers before interpolation; derive canonical paths independently of mutable state. Probe traversal, absolute-path substitution, control characters and forged cleanup targets; unrelated victim files must survive.
- Distinguish progress from terminal results. Success needs the documented outcome and proven real child exit evidence; timeout, silence, truncation or unknown status cannot become success.
- Start a negative fixture from a working positive fixture and alter the relevant fault. A broken prerequisite does not prove the intended gate worked.
- Prove scope confinement in the executor. An unenforced prompt restriction is not a safe execution capability.

Use disposable private roots and controlled doubles for dangerous effects, not production state. State what a double did not test. Keep unproven capabilities out of live descriptions and templates until safely supported.

## Independent judgment for high-impact changes

Changes to security boundaries, destructive actions, publication/deployment authority, credentials or orchestration require a judge who did not produce the candidate. Supply the original requirements, exact candidate, observed artifacts and known gaps, not the producer's verdict.

Distinguish a fresh context from a different model/provider. Use both when the governing project requires them or model-specific behavior is at issue; otherwise state the independence obtained. An unavailable required reviewer or consumer leaves the affected claim blocked, while independent work continues.

## Finish with evidence

For formal acceptance, mark each material item PASS, FAIL or BLOCKED and point to the deciding artifact or observation. For a routine edit, a direct result and its verification are enough. Repair failures at their actual source, rerun invalidated checks and repeat independent judgment after high-impact remediation. Stop when the requested result is supported, or identify the exact missing evidence.
