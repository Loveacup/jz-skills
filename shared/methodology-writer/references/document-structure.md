# 方法论文档结构指南

## 设计理念

方法论文档的结构不应套模板，而应从素材内容中自然生长。不同方法论有不同的最佳表达结构——知识管理方法论可能需要十几章层层递进，AI 思维方法论可能 5 章就够了，工具使用指南可能按功能模块组织更好。

**唯一硬性要求**：思维链（全文逻辑链）和参考引用（来源索引）必须保留。其余章节结构根据内容决定。

---

## 必须项

### 1. YAML frontmatter

```yaml
---
title: "文档标题"
subtitle: "副标题——点明核心框架"
author: "作者名 × Claude"
date: YYYY-MM-DD
version: "1.0"
status: 种子
type: 方法论
tags: [核心标签1, 核心标签2]
---
```

### 2. 思维链 / 全文逻辑链

放在文档开头（速览之后、正文之前），让读者在深入阅读前理解全文的推理路径。

**格式参考**（Obsidian 版用 callout，标准版用引用块）：

```
> [!INFO] 全文逻辑链
> 下面的章节不是并列罗列，而是一条递进的推理链：
>
> ❶ 第一个问题 → 章节名（回答了什么）
> ❷ 上一层留下的问题 → 章节名（回答了什么）
> ❸ ...
>
> 每一层都回答上一层留下的问题。
```

**关键原则**：
- 思维链展示的是**问题链**，不是内容摘要
- 每步回答上一步留下的问题，形成递进
- 标注置信度（高/中高/中）和已知局限
- 思维链决定了章节顺序——如果调换两章顺序逻辑链不通，说明当前顺序是对的

### 3. 参考引用与来源索引

所有核心论点必须有来源支撑。来源索引放在文末附录。

**来源分类体系**：
- 正文引用 `[1]-[N]` 或 `[^1]-[^N]`
- 网络来源 `[W1]-[WN]`
- 公开数据 `[D1]-[DN]`
- 学术论文 `[A-1]-[A-N]`
- 专家观点 `[E1]-[EN]`

**引用完整性**：正文标注 ↔ 附录来源必须一一对应，不允许幽灵引用或孤儿来源。

## 推荐项（按需选用）

### 速览 / 30 秒看懂

在文档开头用 2-3 句话概括方法论全貌。适合长文档，帮助读者快速判断是否值得深读。

### 快速入门

如果方法论涉及实操，提供"N 分钟快速上手"路径。参考 Obsidian 方法论的"10 分钟快速入门"模式：最小可行步骤 → 每日必做 → 每周检查。

### 术语对照表

如果方法论引入了新术语或对已有术语赋予了特定含义，在正文前提供对照表。

### 附录

除来源索引外，可按需添加：
- 效率对比表
- 核心对照矩阵（如认知偏差 × 破解策略）
- 检查清单
- 子文档引用

## 章节组织模式

以下是几种常见的组织模式，可以混合使用。**关键是根据素材内容选择最自然的组织方式，而不是套用固定模板。**

### 模式 A：递进式（问题驱动）

每章回答一个问题，下一章回答上一章留下的新问题。

```
为什么需要？ → 核心原理是什么？ → 怎么做？ → 哪些场景适用？ → 怎么开始？
```

**适合**：从零介绍的方法论（如 STDD 扩散版）

**参考**：STDD 完整方法论——发现→问题→S→TDD→场景→系统→扩散

### 模式 B：分层式（架构驱动）

按从上到下的层级组织：理念层 → 模型层 → 架构层 → 执行层 → 工具层。

```
第一部分：理论基础（理念、认知模型）
第二部分：架构设计（结构、规范、流程）
第三部分：工具生态（工具链、插件、自动化）
第四部分：运维与演进（质量保障、知识复用）
```

**适合**：系统性方法论、有多层抽象的架构文档

**参考**：Obsidian x AI 方法论 v1.7——理论基础 → 核心架构 → 工具生态 → 运维质量

### 模式 C：功能模块式

按独立功能模块组织，每个模块自成一体。

```
核心概念 → 模块1 → 模块2 → 模块3 → 常见陷阱 → 检查清单
```

**适合**：工具使用指南、操作手册、参考文档

**参考**：Skill 制作方法论指南——概念 → 文件结构 → 加载机制 → 类型分类 → 创建流程 → 设计原则 → 常见陷阱

### 模式 D：叙事式

以个人经历/案例为主线，穿插方法论提炼。

```
故事/案例 → 从中发现的规律 → 框架化 → 更多场景验证 → 你怎么开始
```

**适合**：社区分享版、个人博客、演讲稿

**参考**：STDD 社区版——"四十分钟和十三分钟" → 跨领域验证 → STDD 三步 → 场景 → 开始

## 章节内部结构原则

不限定每章必须有哪些固定小节，但遵循以下原则：

### 每章开头点明核心论点

第一句话或第一段就说清楚这一章要讲什么、为什么重要。不要"先介绍背景再引出主题"。

### 概念独立性

如果方法论有多个核心概念（如 STDD 中的 S 和 TDD），**每个概念必须有独立章节或独立大段**。合并讲解会导致某个概念被弱化——这是经过验证的教训。

**检验方法**：删掉其中一个概念的章节，方法论的完整性是否受损？如果受损，说明这个概念需要独立阐述。

### 概念间篇幅均衡

多个核心概念的篇幅应大致均衡（最长不超最短 2 倍）。如某概念在现有认知中更容易被忽视，可适当强化。

### 证据紧随论点

提出论点后立即给出支撑证据。不要把所有证据堆到一个"证据章"里——读者在看到论点的当下就需要被说服。

### 人 AI 角色划分（如涉及 AI 协作）

在涉及人与 AI 协作的章节中，明确划分：
- 人的职责（哪些决策不能让渡）
- AI 的职责（哪些执行可以委托）
- 核心边界（一句话高亮）

### 渐进采纳路径

方法论不应要求读者一步到位。提供从"最小行动"到"完整实施"的渐进路径（Level 0 → Level N）。

### 反模式 / 常见陷阱

方法论越有力，越容易被过度使用。至少列出 2-3 个常见陷阱和规避方法。核心原则：**方法论是手段不是目的。**

## 不同版本的结构差异

### 完整版

- 思维链：完整 5-9 步 + 置信度 + 局限
- 章节：按素材内容自然组织，不设上限
- 证据：六维证据矩阵，3+ 来源交叉验证
- 图表：Mermaid、表格、公式全用
- 附录：完整来源索引 + 效率对比 + 对照矩阵

### 精简版

- 思维链：精简为 3-5 步
- 章节：核心内容合并但保持概念独立小节
- 证据：精选最有说服力的 3 个维度
- 图表：按需保留
- 附录：精简参考列表

### 社区分享版

- 思维链：保留完整的推理路径，用更口语化的表达呈现。社区版的核心是思维，思维链不能被过度简化——它是读者理解全文逻辑的入口。可以精简措辞，但每一步推理必须保留
- 章节：围绕"读者最关心什么"组织，而非完整覆盖
- 证据：行内引用，关键数据保留
- 图表：去掉平台不兼容的（Mermaid → 文字，表格 → 列表）
- 附录：单一参考列表
- 口吻：个人叙事（"我发现..."）替代学术表述（"研究表明..."）
