# 每次使用后的问题与知识循环

本次工作完成、暂停或交接时读取，不等整个项目完结；“一次使用”是有明确范围的一轮工作，不是每条消息或工具调用。轻量问答可以简记，无新增问题或经验就说明，无需造issue或扩建文档。既有授权内主动处理，不让用户提醒每次回写。

把本轮结果连成可再次使用的回路：**项目证据 → 问题归集 / 有条件的知识 → 按需读取 → 下次应用与验证 → 修正或沉淀**。交付完成、反馈闭环完成和公开发布分别认定。无后台监听、定时自动化或默认云端同步；技能未加载时不承诺流程运行。

## 先收拢真实结果

对照本轮目标及最新核心需求，保留实际版本、用户确认、采取的方法、检查和反馈；区分亲自执行、用户报告、引用资料和推断。按[项目组织](project-organization.md)更新当前入口、有效分支、阻塞与下一步，详细证据留原项目。数字交付已完成但实物待验可以如实收尾，不把未做的试装、承重或疲劳试验记为通过。

## 问题进入GitHub，而非消失在对话里

覆盖需求理解、设计/表达、工具、建模、制造、协作交付和技能自身的问题；包括本轮已解决的问题及其方法，不只收报错。纯偏好或正常取舍本身不是故障，不为填表制造问题。

- **确定现有归集点。** 读取项目内已有的反馈定位（仓库、issue与恢复线索）或明确目标；沿用已授权仓库、现有issue与写入方式。配置存在、读成功和写权限分别确认。GitHub管问题/技能改进，项目管理软件或本地记录仍管日常推进；互相链接而不争夺同一状态正本。
- **查重后归集。** 查同主题及已关闭issue；同一原因/改进对象补现有记录，独立问题才新建。所有发现的问题都能对应到issue或明确的待提交项；可用一个主题issue覆盖相关子问题，不按报错次数重复建卡。查重不等于省略新条件、反例或解决证据。
- **摘要足以接手。** 写问题和影响、发生条件/相关版本、预期与实际、已尝试方法、依据、未解决项和验收思路；按问题详略，不强制表格。公开只传可公开且必要的摘要：凭据、私人项目/模型/现场、个人信息、完整对话和日志留本地；第三方资产按许可处理。去敏后无法说明的内容留受控项目记录，issue只保留安全摘要或标记待定。
- **写入后精确读回。** 核仓库、issue编号/URL、提交正文或评论及状态；请求已发送不算成功。结果不明先定位原操作/现有内容，再续传，不能盲目重建。没有目标、权限、可用通道或安全外传条件时，在项目记录待提交内容、原因、已有回执与下一步，继续独立工作，不冒称上传。
- **区分本地修复与远端解决。** 问题已本地修正，记录改动和证据；尚未发布或未覆盖实际使用条件，就保留该限制。创建/补充issue不等于获得推送代码、关闭他人issue或部署权限；已有issue解决状态依其负责人、验收和当前授权处理。

反馈定位是仓库与恢复索引，不复制issue全文或完整项目日志。已有目标暂时断联不另建仓库或悄悄更换正本；恢复后核上次提交再同步。

## 经验写到会被读到的地方

先查当前知识，判断本轮是否带来改变未来决策的事实、方法或条件。经验条目可短，但要能回答：**什么问题 → 在什么条件下做了什么 → 观察到什么 → 适用与不适用范围 → 依据及验证等级**。未证实观察留项目待验证，不包装成经验配方。

| 内容 | 正本与读取入口 |
| --- | --- |
| 尺寸、参数、原始模型、当次机料、未解释现象和详细试验 | 所属项目；在相关参考或案例中按需留链接，不把单次数字变默认值 |
| 能改善同类判断的方法、失败教训及条件修正 | 合并到已有最相关的reference；下次按问题路由能找到，避免同义条目堆积 |
| 可迁移的结构/模块或美学机制 | 按[结构回收分工](project-organization.md#每个项目怎样回收结构)进入结构库、结构卡或美学案例；只抽机制，保留收益、代价和证据 |
| 本地工具运行边界、稳定可重现的漏测/误报 | 当前项目的工具验证记录或工具自身运行说明；区分机器/版本事实与通用结论 |
| 用户明确确认的新需求、偏好或机料条件 | 当前项目核心需求；确有跨项目适用范围才更新相应参考或[打印档案](user-printing-profile.md) |

有新教训就窄幅修改最相关内容，写清旧判断如何改变、条件与未知项；无增量记“无需修改”及理由。新内容需要入口时在相应问题路由链接，不让知识只埋在收尾日志。未通过验证的技能修改保留待验证状态，不能以成功保存文件宣称已生效。

### 下次读取、应用与纠错

接手时从当前目标选相应参考/案例，并核仍未解决且会影响当前决策的问题；不先加载全部历史或每次扫全仓库。核几何、用途、机料、软件版本及证据是否适用，再选择直接复用、局部试用、重新研究或暂不采用。

应用后将实际结果与预期比较。新证据推翻旧方法时，修正相关知识的范围或结论，标明旧结论已被什么证据替代，保留历史来源；同步关联issue/项目入口。原始记录不悄悄改写，也不让已被推翻的规则继续作为无条件当前建议。

## 验证与本轮记录

技能维护先读当前项目的维护需求与变更依据，保留同一主源及并行修改。Dot或其他端提供的经验注明真实来源与读取/执行范围；主源修订、公开发布、副本同步和双方实际加载分别记录，按[协作边界](dot-local-collaboration.md)处理，不为普通产品收尾强制增加同步步骤。

改主技能/参考中的决策规则时：运行当前可用skill格式验证器，检查受影响链接，再对改变的决策做真实或受限场景检验。有脚本变化就运行相应测试。只补项目事实则核来源、入口及参数未被泛化即可；文字情景不等于CAD、切片或实物验证。

先在当前环境定位已有格式验证器，不复制旧机器路径或擅装全局。不可写/不可验证时留下准确路径、完成范围与阻塞。

有成果、问题、经验或待接续事项时，在当前项目已有收尾记录中追加简短条目（细节链接项目记录）；已有同轮条目可补明确的后续结果与日期，不抹旧验证限度。只有进展、阻塞、有效版本或下一步发生实质变化才更新项目状态中自己负责的段落，写前重读并保留其他内容。每次使用交代问题/知识去向；简单问答且无新增内容可仅在答复中简记“无新增问题或经验，无需修改”，不为此更新文件或制造进展。只读任务保持只读，有需处理事项则给出准确待办，不宣称已持久化。

```markdown
## 日期 · 项目 / 本次范围与版本
- 结果与证据：做了什么；亲自执行/用户报告/引用；已验证与未验证。
- 问题去向：GitHub issue/评论链接及读回结果；或待提交位置、原因与恢复线索；无新增则明示。
- 知识去向：相关reference/案例及读取入口、条件/纠正、验证；或无需修改及理由。
- 下一步：剩余工作、责任、验收和当前入口；区分产品交付、反馈闭环、公开发布。
```

项目结束时再检查整套交付/引用和未决问题；无需重复已完成的每次使用回收，也不以总项目未结束为由推迟问题上报与经验回写。
