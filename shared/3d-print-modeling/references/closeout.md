# 收尾与有证据的窄幅迭代

在项目或已完成的数字交付阶段收尾时读取。先重读最新核心需求；文档归档不扩大改模、打印、设备或发布权限。已完成部分和实物待测分开，不为例行本地收尾重复请求已经明确的授权。

1. 关联最终版本、确认/审核依据、实际几何/切片检查与明确反馈，注明亲自执行、用户报告、文档转录或推断。核核心需求、当前README、参考清单、成果与历史能否互相定位；只补本次缺口。
2. 判断有无会改变未来决策的教训。具体尺寸、库存/工艺、原模型、现场事实和未解释现象留项目；不要直接变通用默认。按[结构回收分工](project-organization.md#每个项目怎样回收结构)记录机制的功能、收益、代价和验证等级。
3. 有新增价值就窄幅修正最相关的一段/一张卡，先查重；没有就记“无需修改”及理由。整体方案失败时可研究局部机制，同时保留反证；不因曾交付就写成功结构。
4. 改技能规则时使用当前可用的skill-creator校验器或等价格式检查，并按受影响决策做合适场景核查；新/改脚本实际运行有意义的测试。普通文档事实追加只核来源/链接，不重跑无关制造检查。
5. 在所属项目的复盘记录追加简短结论，更新项目README及项目状态的对应摘要。共享文件写前重读，只合并负责段；历史证据与并行成果保留。向用户交接项目内准确入口与未测项。

项目复盘最少交代来源/最终版本、已验证与未验证、明确反馈、新教训或无需修改、更新位置及实际核验。未做的试装/承重/疲劳不能记通过。收尾记录保存在项目目录，具体位置可沿用已有体系，不把私人日志写进已安装或公开的技能包。

由Dot协调时，两端经验交同一维护者，记录主源修改、公开发布、副本同步和双方实际读取各自的状态；哈希支持身份，不代替加载或实际工作。没有明确新授权就不自动上传、定时轮询、全局部署或变更外部副本。本流程随任务收尾执行，不是后台自动化。
