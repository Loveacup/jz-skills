# 报告与交付

适用于阶段 5：成文、画图、导出 PDF 与发送。

## 成文

- 按读者最关心的问题组织，先给结论。每个主结论都要能追溯到数据、推理和失效条件，但不必逐条套用同一个四段格式。
- 摘要、图注、正文各有分工：摘要给判断，图注写口径和关键读数，正文解释含义。同一组数字不在摘要、逻辑链、正文、风险表里反复重述。
- 概率和信心分开写：「可能性」说结果发生的机会，「信心」说证据的质量。用「很可能」等词时全篇含义一致；有模型输出就给数值或区间，没有就写依据和不确定来源，不编造百分比。
- **引用：** 正文只写编号链接 `[E01][]`，链接定义统一放在文末（`[E01]: URL "标题"`）；来源表列出编号、来源、披露日和引用页码。callout（`> [!...]`）里的链接 2pdf 不解析引用式写法，要写成内联链接 `[E01](URL)`。本地计算产物也编号（F01…），链接到 `data/` 下的文件。
- **笔记属性：** 按模板填写 frontmatter，给 Obsidian 使用。署名 `author` 默认为 AlexCai，每份报告都加；用户另行指定时才改。`cli`、`models`、`model_roles` 只写实际参与的 CLI 和模型（包括子代理），以运行记录或会话日志为准，查不到就写「未记录」，不猜；`algorithms`、`software`、`random_seed` 只写实际运行过的方法和版本。导出 PDF 时加 `--byline`，在标题下显示署名、CLI 与模型；不加 `--properties`，避免属性卡占掉首页。
- **文件名：** Markdown 与 PDF 同名，格式为 `<公司名>-<代码>-<研究主题>-<资料截至日>`，如 `胜宏科技-300476.SZ-2026Q4股价情景与基本面研究-2026-09-27.pdf`；不用 `report.pdf` 这类通用名，方便在手机和文件夹里识别。
- 正文结尾（附录之前）写明作者与标的的利益关系（持仓、报酬、业务往来）和免责声明：没有已知关系时写明「无已知利益关系」，未核实时如实写。研究范围与未覆盖事项写在开头的「研究范围与口径」里。本报告是独立研究，不冒称持牌机构研报。

## 图表

根据证据需要选图，不要求固定数量。常用图：

|图|何时需要|
|---|---|
|利润/现金流趋势|任何基本面报告|
|同业估值对比|使用相对估值时|
|情景矩阵或敏感性热力图|情景目标价或反向 DCF|
|预测扇形图|有预测分布时|
|覆盖率与宽度|有回测时|
|催化剂时间线|有已确认或预约的事件时|

- 图表由单独的绘图脚本（如 `data/build_figures.py`）只读取 `data/` 下已保存的计算产物生成，不与模型脚本耦合，改图时不必重跑模型（matplotlib 等绘图库，或库不可用时由脚本直接写 SVG）；正文数字引用同一产物，不单独手抄。不为画图擅自安装依赖；绘图库缺失且无法用脚本生成图时，报告图表阻塞。
- 每张图的标题直接写出结论（如「收入仍在增长，扣非利润增速回落」），而不只是指标名。来源写在 Markdown 图注里，不画进图片底部，以免与坐标轴标签重叠。图号按正文出现顺序连续编号，调整章节顺序后要重排。
- 每张图下方写：图号与标题、单位、数据时间、来源，以及一句结论性解释。
- 中文字体：使用本机已安装的 CJK 字体（如 PingFang SC、Hiragino Sans GB、Noto Sans CJK、Microsoft YaHei）；用 matplotlib 时先经 `font_manager` 确认字体存在，并设置 `axes.unicode_minus=False`。数据标签不能被标记点或线遮挡。
- 尺寸适合 A4：宽约 16 cm、dpi ≥ 150；在 Markdown 中用 CSS 限制图片最大高度，避免一图占满整页。不只靠颜色区分系列，也不只用红绿区分涨跌或情景；加直接标签、线型或形状，保证灰度下可读。
- 坐标轴标明单位与尺度。柱状图必须从零起轴；折线图不从零起轴或用对数轴时，在图注说明理由。不用双纵轴，改为并排的小图（如收入、利润、利润率各一个面板）。
- 预测扇形图在图例中标出各色带的分位数或名义覆盖率、中心线含义（中位数或均值）、价格口径与日期，并说明色带是每日的边际区间，不是窗口内触及的概率。
- 预测任务采用两层 Mermaid：开头的目标问题总图区分价格口径、统计分布、回测校准与基本面条件，量化章节的模型计算链说明数据 → 验证选模 → 封存测试 → 当前拟合/模拟 → 交易约束 → 输出。只画实际运行步骤与证据，不把未校准区间写成保证，不把基本面情景暗示为已混入统计路径；用同一套节点语义和克制的配色，A4 上文字可读。
- 表格每个单元格只放一个数字，不写「66.7% / 44.73%」这类组合；单位放在表头或指标名里（如「TTM 市盈率（倍）」），数值列只放数字；来源列只放编号，口径说明写在表下。超过 6 列的表拆成两张。窄列（如「状态」）并入相邻列。逐页检查时专门看数字有没有被折行拆开（如「+1.」「47%」分在两行），发现就改表再导出。

## 一致性检查（导出 PDF 前）

列出正文中的每个关键数字，写上对应的证据编号（如 `E03`）或 `data/` 中的计算产物，逐一比对；检查图中标注的值与正文一致。找不到来源的精确数字，删除或改为定性描述。不一致时先修正再导出。

成文后做一次质疑复核，最好交给没有参与写作的新代理：专查公司和证券代码是否对应、关键日期和数字、每条核心判断最强的反例。复核只能指出问题或删改，不能补入没有来源的新事实。

## 导出 PDF

1. 读取已安装的 `2pdf` 技能的 SKILL.md，并确定该技能的真实目录。
2. 按 2pdf 的说明运行预检（`--preflight`）；依赖缺失时允许它自带的环境引导。
3. 运行：

   ```bash
   python3 <2pdf 技能目录>/scripts/md2pdf_chrome.py "<文件名>.md" "<文件名>.pdf" "<页眉标题>" --page-size A4 --theme academic --verify --byline
   ```

4. `--verify` 只检查文件质量门（Mermaid 泄漏、页数、元数据等），不是视觉检查。还要把全部页面渲染成图片逐页查看，例如 `pdftoppm -scale-to 1400 -png "<文件名>.pdf" page`。没有 pdftoppm 时，用 2pdf 环境里的 Python PDF 渲染库（如 pypdfium2）。检查中文是否正常显示、图例、表格是否溢出、分页、正文数字。
5. `--preview` 只导出第 1 页和含命名图表的页，不能作为「已检查全部页面」的依据。
6. 发现问题后修改 Markdown 再导出，不插入强制分页。常见排版问题的改法：大图或 Mermaid 被整块推到下一页、留下半页空白时，调整图的位置或高度；只剩免责声明孤立在最后一页时，把利益关系和免责声明放到附录之前；附录较长时可加 `--sm "附录"` 缩小字号。

依赖无法安装或渲染失败：报告「Markdown 完成，PDF 阻塞」，附上错误信息；不把未生成或未检查的 PDF 说成已完成。无法做视觉检查时，同样写明「视觉验收阻塞」。

## 发送

只有当用户在当前请求中指明要发送的文件和收件方时，才读取 `blip-transfer` 技能，并按它的初始化、授权和状态规则执行。本技能不重复它的发送步骤。

- Pending、Waiting、Active、Invited 都不等于已送达。只有该传输的 Completed 状态或收件人确认才算送达。
- 自测、演示和验收中不发送任何文件。
